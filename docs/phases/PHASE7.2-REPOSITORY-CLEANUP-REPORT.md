# Phase 7.2 — Repository Hygiene, Storage Audit & Safe Cleanup

**Date:** 2026-09-16
**Scope:** Storage forensic audit + safe cleanup of Competitor Monitor AI working directory.
**Status:** PASS

---

## Executive Summary

The headline finding of this audit is that **the Git repository itself was never the problem.**

`.git` measures **871 KiB** (698 loose objects, no packs) and `git ls-files` lists only **276
tracked files**, the largest of which is `package-lock.json` at 148 KB. There is no history
bloat, no accidentally committed binaries, no vendored external repositories, and no secrets in
tracked content. `.gitignore` was already correctly excluding every build/cache/local-infra
directory before this audit began.

The reported ~2.58 GB (measured at audit start as **2.8 GB**, growth explained below) is
**100% untracked, local-machine, disk-only material** — reproducible build caches, npm
dependencies, and a documented native Postgres/Redis dev environment. None of it reaches the
remote when the developer pushes; all of it was already invisible to `git status`.

One item — the Next.js **`next dev` incremental Turbopack cache** — had grown unbounded to
**995 MB** because it accumulates indefinitely across `next dev` sessions and is never
auto-pruned. That single directory was **91% of the entire reclaimable disk footprint** and is
fully regenerated by the next `npm run build` / `npm run dev`. It has been removed.

| Metric | Value |
|---|---|
| Initial size (`du -sh .`) | 2.8 GB |
| Final size (`du -sh .`) | 1.9 GB |
| Space reclaimed | ~995 MB (≈ 995,000 KB) |
| Reduction | ~34% |
| Git repository size (`.git`) | 871 KiB — unaffected, was never the issue |
| Tracked files | 276 — unaffected |

> Note on "2.58 GB" vs. the 2.8 GB measured here: the `.next/dev` cache this audit removed grows
> monotonically with every `next dev` session (it is Turbopack's incremental compile cache, never
> auto-pruned). The gap between the figure quoted in the task and the figure measured at the start
> of this session is consistent with a few additional `next dev` runs between when "2.58 GB" was
> last observed and when this audit started. The mechanism, not the exact number, is what matters
> here, and it is now understood and fixed.

## Decisions

### KEEP — production source & required configuration
`apps/web/src`, `apps/web/e2e`, `apps/worker/src`, `packages/*/src`, `packages/db/prisma/schema.prisma`
and `prisma/migrations`, `package.json` / `package-lock.json` / `tsconfig.base.json`,
`docker-compose.yml`, `.env.example`, `scripts/validation/*`, `README.md`, `DevRunbook.md`, and the
`PHASE*.md` implementation/validation reports. All are genuinely load-bearing and none are
oversized (largest tracked file: `package-lock.json` at 148 KB).

### KEEP — local, documented, reproducible dev infrastructure
`.local-infra/` (Postgres + Redis native binaries, 943 MB) is already gitignored and its purpose
and provenance are explicitly documented in `DevRunbook.md` §3 ("Database & queue — getting
Postgres/Redis running") as the no-Docker fallback path, cross-referenced from the
`.gitignore` comment itself. This is intentional machine-local tooling, not repository bloat.
`.local-infra/pgdata/` (67 MB) additionally holds the developer's actual local database contents
— it was **not** touched, per the "do not delete live/non-reproducible state without asking"
rule in this audit's instructions.

### KEEP — reproducible dependency/build caches needed for current work
`node_modules` (all workspaces) and `packages/db/generated/` are correctly gitignored,
reproducible from `package-lock.json` and `prisma/schema.prisma` respectively, and are actively
required for the app to typecheck/build/run in this session. Deleting them would not shrink the
*repository* (they were never tracked) and would only force a lengthy, network-dependent
reinstall for zero git-hygiene benefit — outside this phase's actual objective.

### REMOVE — regenerated, unbounded build cache
`apps/web/.next` (995 MB) — Next.js/Turbopack's incremental dev-server cache
(`./.next/dev/cache`, 510 MB) plus stale build output. Confirmed:
- Not tracked by git (`git ls-files | grep -c '\.next'` → 0).
- Fully reproducible: `npm run build --workspace apps/web` regenerated a clean, working
  `.next` directory of **91 MB** (vs. the 995 MB dev-accumulated one) — proof that the size was
  cache accumulation, not a legitimate build requirement.
- No consumer references files inside `.next` from outside the Next.js toolchain.

**Action taken:** deleted. See Validation section for the rebuild proof.

### No REVIEW items
Every large or ambiguous asset found during this audit resolved cleanly to KEEP or REMOVE. No
abandoned experiments, no `backup`/`old`/`poc`/`vendor`/`reference`/`scratch`/`temp` directories,
no duplicate repositories, and no unidentified large files were found anywhere in the working
tree outside the categories above.


### C. Cleanup action
```

```

### D. Build (post-cleanup, proves reproducibility)
```
npm run build --workspace apps/web   → succeeded, regenerated apps/web/.next at 91 MB
npm run build --workspace apps/worker → succeeded (tsc compile to dist/)
```
The rebuilt `.next` (91 MB, real production output) vs. the removed one (995 MB, months of
accumulated Turbopack dev-cache) is itself the proof that the removed material was pure cache
bloat, not a build dependency.

### E. Post-build tracked-file diff review
`next build` regenerates the tracked file `apps/web/next-env.d.ts` with dev-mode vs. build-mode
type-reference paths (this file is Next.js-managed, marked "should not be edited," and normally
just reflects whichever of `next dev`/`next build` ran most recently). Since this cleanup's
intent was storage hygiene, not a source change, that incidental diff was reverted via
`git restore` so this phase leaves zero unrelated changes in git history.

## Conditions / Follow-Up (optional, not executed in this phase)

- If a developer wants to reclaim the `node_modules`/`packages/db/generated` space on a machine
  where the project is not actively being worked on, `rm -rf node_modules packages/*/node_modules
  packages/db/generated && npm install && npm run db:generate` is safe and fully supported by the
  lockfile/schema — not executed here because it offers no repository benefit and would require
  a live network dependency mid-audit.
- Recommend periodically clearing `apps/web/.next` (e.g., `rm -rf apps/web/.next`) during long
  `next dev` sessions, since Turbopack's dev cache has no automatic size cap and will re-grow
  over time — this is Next.js's own behavior, not something this repository's configuration can
  change.
- No `.next/cache` size cap or CI hygiene job currently exists to prevent recurrence; adding one
  (e.g., a periodic `rm -rf apps/web/.next` in a dev-machine cleanup script) would be a reasonable
  small follow-up but is outside this phase's scope.
